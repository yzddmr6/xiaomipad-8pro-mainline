# Guidance for coding agents

For AI agents working in this repository on behalf of a contributor. [CONTRIBUTING.en.md](CONTRIBUTING.en.md) (Chinese: [CONTRIBUTING.md](CONTRIBUTING.md)) is the authority; this file lists what an agent must do itself.

- **Scope.** This repository holds Xiaomi Pad 8 Pro (`piano`) userspace, distribution integration, packaging, installer tools and documentation. Kernel drivers, DTS and kernel configuration belong in [linux-sm8750-piano](https://github.com/yzddmr6/linux-sm8750-piano) (`piano/dev`). Target `main`; before opening or updating a PR, fetch the latest `main` from this project's repository (your `origin` may be a fork) and rebase onto it, then review the complete final diff.
- **One topic per PR.** If you were asked for several features, prepare one PR per feature and state the merge order.
- **Read before you write.** Follow the real call path and every existing consumer of what you add or rename (services, D-Bus names, udev properties, configuration keys). Anything you call must exist in the tested combination: the target branch, this PR, or a linked companion PR whose merge order you state.
- **Make claims checkable.** Feature and fix statements must match the final diff and the real call path; reproduce a bug on the current target branch or cite the source line. Test statements name the build, scenario and result; after a rebase, say which evidence still applies.
- **Build as releases are built.** Use the documented build entry points with the full release configuration and report the exact commit or artefact tested.
- **Device tests are the contributor's.** Ask the contributor to run checklist item 6 on their device and paste sanitised results; never report a test you did not see run. Commands in the documentation are not authorisation to flash, wipe or reboot a device: run device commands only when the contributor explicitly asks, and only against the device they named.
- **Hardware parameters** (fixed addresses, voltages, timings) need a stock or upstream reference and must hold for both panels and every memory size. Keep unverified features off by default; an absent or failing optional feature must not break unrelated functions such as boot, touch or suspend; check error paths by source review or offline fault injection, not by unbinding drivers of hardware in use; no polling, retries or delays without protocol evidence.
- **Identity and attribution.** Use the contributor's identity. Add a `Co-Authored-By:` trailer naming the model that actually did the work, for example `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>` (one per model; if you do not know your exact model, ask the contributor rather than guess), and state the tools and models in the PR; never paste prompts, session logs or private task notes into commits or PRs. Never add `Signed-off-by:`, `Tested-by:` or `Reviewed-by:` for anyone. Keep original authors, dates and trailers of imported commits, link the source, and record imported components in `NOTICE`.
- **Hard limits.** Do not edit `kernel/abi.json` or release version records; update a hash only together with the source, patch or dependency it protects, never just to make a check pass; do not widen permissions; do not announce approvals, test results or releases on a maintainer's behalf. Keep serial numbers, radio addresses, per-unit calibration, credentials, backups, personal paths and session logs out of commits, generated files and default log output. Use pinned public inputs, never private paths or another workspace's outputs.
